# Commands are a work queue with a shelf life; Events start from now

The commands stream uses JetStream's work-queue retention: a Command is deleted the moment it is acknowledged. This is deliberate, for three reasons. It keeps the stream self-cleaning — an executed Command is finished work, and pure cost to keep around; under time-based retention it would linger for the full retention period regardless of having been handled. It turns the stream's depth into a live backlog signal: "still in the stream" becomes equivalent to "not yet done", so the depth of `cqrs-commands` is the backlog of unexecuted work, readable straight off NATS — a number time-based retention would instead mix done and pending Commands into, meaning nothing. And it lets the broker, not mere convention, enforce that a Command is addressed to exactly one logical handler: JetStream refuses two consumers with overlapping filter subjects on a work-queue stream (`JSConsumerWQConsumerNotUniqueErr`, error code 10100), while still letting replicas of one service share load, because they share the one durable consumer that name produces — what is forbidden is two *different* consumers competing for the same Command, not replicas of the same one.

A work-queue stream carries a further, unconditional constraint, one we found from a failing integration test rather than from documentation: JetStream rejects any non-mirror, non-sourcing consumer on it whose delivery policy is not `DeliverAll` (`JSConsumerWQConsumerNotDeliverAllErr`, error code 10101, "consumer must be deliver all on workqueue stream" — nats-server's `server/consumer.go`). There is no escape hatch. This is coherent with why the stream is a work queue in the first place: `DeliverNew` on it would let a queued Command be permanently skipped by a new consumer — never delivered, therefore never acknowledged, therefore never deleted — accumulating in the stream forever. JetStream refuses to let that trap be built.

Because a Command can sit in the stream for a while before its consumer exists or catches up, and a stale Command is not always still safe to execute, the commands stream also carries a 24-hour age limit: a Command older than that is discarded instead of delivered. `DeliverAll` plus that age limit is not a concession to the server's constraint — it is CONTEXT.md's own Command entry, made literal: a Command is "kept until it is handled — or until it is old enough that doing it would no longer be right." `DeliverAll` is the "kept until it is handled" half; the age limit is the "old enough" half. The decision this ADR originally recorded — `DeliverNew` for Commands — contradicted that glossary entry; the change forced by the server made the code more faithful to it, not less.

Events are the opposite case, and keep `DeliverNew`. The events stream uses time-based retention (7 days) and fans out to one durable consumer per Handler, so `DeliverNew` is permitted there, and is what we want: an Event is history, and a Handler that comes into existence today is not owed the past. Without it, a newly deployed Event Handler would be flooded with up to 7 days of backlog on its first start. `DeliverPolicy` only takes effect at consumer creation; on restart the durable already exists and resumes from its own stored position, so `DeliverNew` never causes loss across restarts.

## Considered Options

- **Time-based retention for the commands stream**, which would permit `DeliverNew` for Commands and deliver, literally, "a new Handler sees nothing old." Rejected, and not merely on aesthetics: without a work queue's non-overlapping-filter rule, renaming a Command Handler during a rolling deployment leaves old pods on the old durable and new pods on a new one — and both durables match the same filter subject, so both receive every Command, and each Command is executed twice, silently. The work queue turns that into a loud startup failure instead (see Consequences). Time-based retention would also give up the self-cleaning stream and the backlog-depth signal described above.
- **`DeliverNew` for Commands on the work-queue stream** — the decision originally recorded here. Not rejected on judgement: rejected by the server, error 10101.

## Consequences

- A brand-new Command consumer executes every Command still queued from the previous 24 hours. This is materially weaker than "a new consumer never executes a Command queued before it existed" — the age limit bounds the damage, it does not prevent it. A Command queued 23 hours before a new consumer is created is still executed. The limit is configurable (`WithCommandsMaxAge`); a domain where executing stale work is dangerous should shorten it.
- A Command can expire without ever being executed. This is intended.
- Renaming a Command Handler is a startup failure, not a silent skip. The durable consumer is named `serviceName_handlerName`, so a rename creates a new consumer while the old durable — nothing deletes it — still holds the same filter subject; a work-queue stream rejects that overlap with error 10100. The old durable must be deleted before deploying the rename. This failure is protective: it is the loud form of the silent double-execution described under the rejected time-based-retention alternative above.
- Renaming an Event Handler is different, and permitted: the new consumer is created fresh with `DeliverNew`, silently skipping everything that was pending under the old name.
