# A cache entry lives as long as its substrate says

A Cache here is a memo of an expensive answer — an agent's resolved identity, a customer row read on every request — kept where every replica can find it. The obvious shape for one is a `Set(key, value, ttl)` map, and this library deliberately does not have it. The KV contract is `{Get, Put, Delete}` with no time in it at all: the substrate is constructed with **one static TTL for every entry it will ever hold**, which is the in-memory store's constructor argument and, on JetStream, the bucket's `MaxAge`. One bucket is one Cache, the bucket is the Cache's namespace, and a write is a plain idempotent `Put` that a server of any version accepts. Per-key TTLs on JetStream KV mean `KeyTTL` and `LimitMarkerTTL`, which mean NATS 2.11 or later and a per-entry limit marker on the stream — machinery whose only purpose would be letting one Cache hold entries of two different lifetimes, which is two Caches wearing one bucket. Reintroducing per-entry TTL is a one-way door: it changes the KV contract for every implementation, so it stays shut until something actually needs it.

The static TTL leaves one real gap, and the **hit validator** is the answer to it: some values die on their own schedule, before the substrate's — a cached token reaching its own `exp` claim is the case that forces this. A hit the validator refuses is treated as a miss, so the Loader runs and its result overwrites the entry. The Cache never inspects a value's contents itself, because it does not know what V is; the caller supplies the predicate. What this deliberately does not do is make the Cache the correctness boundary for expiry: whatever verifies a token downstream is still the thing that must reject a dead one. The TTL and the validator are staleness knobs, not security ones.

A Cache is an optimisation, so it fails like one. When the substrate returns anything other than `ErrNotFound` — the broker is unreachable, the bucket was deleted underneath us — `Get` calls the Loader and returns its result **uncached**, and the caller sees latency rather than an error. The mirror of that rule is that a Loader error is never stored: a failure is not an answer, so the next caller tries again. That also settles negative caching, which this library does not do at all. It is not an oversight: a negative key space is whatever callers ask for, which for anything authentication-shaped means whatever an attacker sends, so remembering rejections in an unbounded substrate turns a flood of bogus keys into unbounded memory. If negative caching is ever added it has to arrive with a bounded substrate, and the classification of which failures are definitive has to come from the caller, which alone can tell "no such key" from "the database is down".

Concurrent misses on one key share a single Loader call, because the stampede is the whole problem: a cold cache under load is exactly when N replicas each decide to ask the expensive question. Waiters select on **their own** context, so a caller that gives up is not held by the flight — but the Loader itself runs under the context of whichever caller started it, and if that one is cancelled the shared call is cancelled with it. A caller that cannot afford that wraps its Loader in `context.WithoutCancel`; the Cache does not do it for them, because detaching every Loader from every context would leak work no one is waiting for.

## Considered Options

- **Per-entry TTL in the KV contract (`Put(key, value, ttl)`).** Rejected: on JetStream it requires NATS ≥ 2.11 and per-key TTL markers, and it buys only the ability to mix lifetimes inside one Cache — which is better expressed as two Caches with two buckets, at no cost.
- **An in-process cache library (`groupcache`, an LRU, `sync.Map` plus timers).** Rejected as the only substrate: it gives every replica its own copy, so N replicas mean N loads per TTL and N different answers during a rollout. It survives as `cache.Memory`, which is the substrate for tests, dev and single-process services — and the dependency-free documentation of the KV contract.
- **File storage for the KV bucket.** Rejected: cache entries are disposable by definition, the Loader rebuilds any of them on demand, and a broker restart costing a cold cache is cheaper than every cache write costing a disk write. Buckets are memory storage.
- **Event-driven invalidation instead of a TTL.** Deferred, not rejected: publishing an Event on revocation and evicting the entry would shrink the staleness window to a delivery, at the cost of a new Event, a subscriber per Cache, and a missed-delivery failure mode that leaves a stale entry until the process restarts. The TTL is the self-healing floor that needs none of that; `Delete` is the primitive such a subscriber would call, and it exists for exactly that reason.

## Consequences

- A change to the underlying data is not visible for up to the substrate's TTL. That window is the Cache's entire cost, it is chosen once per bucket, and it must be an acceptable staleness for **every** key in that bucket — which is what "one bucket per Cache" really means.
- A restart of the broker empties every cache bucket, and so does deleting one. Both are recoverable by definition: the next `Get` misses and the Loader repopulates it.
- The Cache itself never calls `Delete`. It exists on the KV contract for callers that evict out of band, and for the event-driven invalidation deferred above.
- Values round-trip through `encoding/json`, so a V that does not survive marshal/unmarshal is silently degraded rather than rejected — an entry that fails to decode is treated as a miss, which turns a bad V into a permanently cold cache rather than a wrong answer.
- `natskv` binds its buckets with the `cache_` prefix, so a cache bucket and its `KV_cache_*` stream are recognisable in the broker at a glance, and an already-prefixed name is refused rather than doubled.
