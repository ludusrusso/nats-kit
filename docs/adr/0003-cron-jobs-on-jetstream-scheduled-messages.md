# Cron Jobs are scheduled by the server, not by the process

A Cron Job's Schedule is kept by NATS, not by a `time.Ticker` in the process that declares it. The runner publishes a schedule-definition message carrying a `Nats-Schedule` header and a target subject; from then on the **server** generates a Tick on that subject at every firing, and a durable consumer shared by every instance of the job delivers each Tick to exactly one of them. This is what makes a service declaring Cron Jobs horizontally scalable: with in-process ticking, every replica ticks, so every job runs N times per firing unless the deployment is pinned to one replica or every handler is written to claim its work defensively. It also makes a Schedule outlive the process — a deploy no longer resets a long interval's phase, and a job's next firing is broker state, not the age of a goroutine.

One **durable consumer per job**, named `cron_<namespace>_<job>` and filtered on that job's Tick subject, is what buys single delivery and failover at once: replicas compete for the same consumer, so a Tick goes to whichever is free, and an instance that dies mid-Tick has its unacknowledged Tick redelivered to a survivor without any leader election. That consumer is created with **`MaxAckPending: 1`**, which preserves, now cluster-wide, the guarantee an in-process ticker gave implicitly: a job never overlaps itself. The next Tick waits for the previous one's ack, so a handler that outruns its own interval delays its next run rather than racing it. `AckWait` is a generous fixed constant (five minutes) rather than per-job configuration — it is a bound on how long a lost instance's Tick stays stuck, not a tuning knob for handler duration.

A Tick carries a **TTL of five times its job's interval**. Ticks generated while nobody was bound to the consumer would otherwise queue indefinitely, so a job that ticks every minute and an outage of a day would come back to a thousand-Tick catch-up burst. Expiring them server-side turns that into a bounded burst: a handful of missed firings, then the ordinary cadence. A cron expression has no single interval, so a job declared with one keeps the server's default Tick TTL.

**The broker converges to what the code declares.** At startup the runner purges the Schedule and deletes the durable consumer of every job that its namespace no longer declares, so removing or renaming a job does not leave an orphan generating Ticks nobody handles, forever. Reconciliation is scoped to the one namespace a Runner owns and matches consumers by their filter subject, which is unambiguously dot-tokenised, so it never reaches into another namespace's state. A Schedule is republished **only when its expression changed**: a republish replaces the definition and is assumed to reset an `@every` phase, so republishing unconditionally on every rolling deploy could postpone a thirty-minute job indefinitely. Comparing first removes any dependence on that behaviour, and an unchanged deploy leaves a running cadence exactly where it was.

A handler that returns an error is **logged and acked**, not redelivered. Redelivery is actively wrong here: with `MaxAckPending: 1` a Tick being retried occupies the job's only in-flight slot, so a persistently failing handler would stall its own Schedule instead of merely failing on it. Acking means the job simply runs again at its next Tick — the same thing a failed run of a cron job has always meant — and one broken job cannot tear down the process it shares with a `natsjs.Runner`.

## Considered Options

- **In-process ticking with leader election** (a Kubernetes Lease, a NATS KV lock). Rejected: it introduces coordination infrastructure and its failover edge cases only to keep scheduling in-process, where deploys still reset timers, Schedules still have no persistence, and one elected process still does all the ticking.
- **Platform cron** (Kubernetes CronJobs or equivalent). Rejected: each job becomes a separate process with a cold start per firing, outside the wiring of the service that owns the work, and declared in deployment manifests rather than in the code next to the handler. That is a different product, not this library.
- **Redelivering a failed Tick** instead of acking it. Rejected for the reason above: under `MaxAckPending: 1` a retry blocks the Schedule, converting "this run failed" into "this job stopped".
- **Republishing every Schedule on every startup**, which would be simpler than comparing first. Rejected: it makes a rolling deploy able to postpone a long-interval job forever, and the phase-reset behaviour it relies on is not documented.

## Consequences

- This package hard-requires **a NATS server that supports scheduled messages** (2.14 or later). There is no in-process fallback: without `AllowMsgSchedules` on the stream, nothing ticks.
- There is **no immediate run at startup**. A brand-new job first fires one full interval after it is registered, and a restart does not re-run anything.
- The `cronjobs` stream is provisioned with `CreateOrUpdateStream`, diverging from `natsjs.EnsureStreams`, which creates a stream only if it is missing and never reconfigures one that exists. That rule protects shared infrastructure; this stream is not shared — it is wholly owned by this package and useless without `AllowMsgSchedules` and `AllowMsgTTL`, so a stream left over from a version that lacked either is upgraded in place rather than silently producing Cron Jobs that never fire.
- **A handler failure's only signal is a log line** — Error level, carrying the namespace and the job — not a metric. This library takes no metrics dependency, so a job failing on every Tick becomes an alert in the caller's `slog` handler or nowhere. A deployment that cares must route these logs; nothing crashes, and nothing counts.
- One Runner owns exactly one namespace. Two deployments sharing a namespace while declaring different jobs would each reconcile the other's Schedules away; a namespace belongs to one process.
- Orphans are reconciled at startup, so anything that escapes reconciliation (a namespace that no process registers any more) shows up as a consumer with an ever-growing pending count.
