# An Aggregate records; whoever persists it drains

Domain code that decides something also produces the Events that say what it decided, and it is the one place in this library that has no business knowing how a Message leaves the process. So an Aggregate is a buffer and nothing else: `Record` appends an Event, `PullEvents` hands the batch over and forgets it, and publication is a separate act performed by whoever persists the object — `Drain(ctx, sink, src)`, which is one `EventBus.Publish` on everything `src` had recorded. The `sink` is a parameter, because that is what makes the Outbox and the transport interchangeable at the only place the difference matters: a repository saving inside a transaction passes the Outbox `Publisher` bound to that transaction, a caller with no transaction passes the transport's, and the aggregate is byte-for-byte the same object in both cases. The alternative direction — teaching a Publisher, or the Outbox, to accept an aggregate — would push a domain concept into every transport and every application's Outbox implementation, to replace an argument that is already there.

The buffer has exactly one rule, and it is the pull: a pulled Event is gone from the aggregate, so a fact leaves once no matter how many times somebody drains. The empty case is deliberately silent — `EventBus.Publish` with no Events touches no Publisher — so a repository drains unconditionally after every save, rather than asking each aggregate whether anything happened. Recording order is preserved into a single `Publish` call, which for an Outbox `Publisher` means one transaction, either wholly written or not at all; beyond the Publisher it is not preserved, and ADR 0002 already records why the Outbox promises no downstream ordering.

`Drain` takes Events and only Events, and the asymmetry with `cqrs.Publisher` — which carries both kinds — is the point rather than an omission. An aggregate states facts about itself; a Command is an intent addressed to exactly one handler, formed by whoever decides what should happen next, and an object recording what just happened is not that. The mechanical difference agrees: an Event recorded now and published on commit is still history when it lands, while a Command has a shelf life (ADR 0001) that a long transaction eats into, so buffering intents would need a decision about staleness that recording facts simply does not raise.

## Considered Options

- **The Publisher in the context** — `cqrs.WithPublisher(ctx, pub)`, with aggregate methods publishing as they record. Rejected, and it is the reason `Drain` has a `sink` parameter at all: the dependency becomes invisible, so a call path that never injected a Publisher still compiles and still runs, and silently drops every Event the aggregate recorded. That is the exact failure the Outbox exists to prevent, reintroduced one layer above it. On the signature there is no path that forgets.
- **An aggregate-aware Publisher or Outbox** — `Publish(ctx, aggregate)`, or an `Outbox` method taking an `EventSource`. Rejected: it teaches a domain concept to every transport and to every application's own Outbox, N implementations of one behaviour, in exchange for nothing the caller cannot already write in one line. `Publisher` stays a sink for Records, which is what keeps it the single seam.
- **`Drain` accepting Commands as well**, via a second source interface or one source yielding both. Rejected on the semantics above, and because the door only opens one way: a Command drain can be added later without touching this one, whereas an `EventSource` that has learned to yield intents cannot be narrowed again.
- **A fuller aggregate base type** — identity, version, `Apply`, rehydration from its own past Events. Rejected: that is an event-sourced aggregate and this library is explicitly not an event store. The mixin buffers what an operation recorded; it owns no lifecycle, no history and no state transitions.

## Consequences

- The `Publisher` handed to `Drain` decides the guarantee, and nothing checks that the choice was right: draining a transport `Publisher` from inside a database transaction publishes Events for a change that can still roll back. That is the seam doing its job, not a gap in it — the caller who opened the transaction is the only one who knows.
- A `Drain` that fails has already emptied the aggregate, because the pull precedes the publish. Retrying the `Drain` alone republishes nothing; the unit of work is what retries, rolling back and rebuilding the aggregate from state.
- An Aggregate carries no lock and is not safe for concurrent use. One aggregate belongs to one goroutine for the length of one unit of work, which is how a domain object is handled anyway.
- The zero value is ready to record, so embedding it needs no constructor and no initialisation step an aggregate's own constructor could forget.
- Every Event drained through an Outbox inherits at-least-once delivery and no ordering guarantee (ADR 0002). Recording order is a property of the batch handed to the Publisher, and callers must not read it as a property of what handlers eventually see.
